\begin{abstract}
Denial of Service (DoS) and Distributed Denial of Service (DDoS) attacks aim to diminish the availability of a service by exhausting finite resources required by legitimate users. These critical resources include worker threads, memory buffers, CPU time, and application concurrency slots. This laboratory experiment presents a safe, local, and reproducible demonstration implemented in Python using a multithreaded Flask HTTP server and controlled traffic generators. A web browser acts as the legitimate user client. Under baseline conditions, the user interacts smoothly with the web interface and executes health checks. During an attack scenario, the traffic generator dispatches rapid requests to an expensive workload endpoint (\texttt{/work}) until all active worker slots ($C = 4$) are occupied. Subsequent legitimate browser probes to \texttt{/health} encounter immediate HTTP 503 Service Unavailable responses. Upon stopping the attack stream, the server promptly recovers to normal operating capacity. Quantitative metrics, interactive browser UI screenshots, and defensive countermeasures are presented.
\end{abstract}

\section{Introduction}
Denial-of-Service (DoS) and Distributed Denial-of-Service (DDoS) attacks represent fundamental threats to the availability pillar of the CIA (Confidentiality, Integrity, and Availability) security triad. By flooding a target with excessive connection requests or computationally demanding tasks, adversaries exhaust finite hardware or application-layer capacities. The visible outcome is elevated latency, connection timeouts, rejected requests (HTTP status 503), or total service outages.

This assignment implements a safe, controlled classroom demonstration on localhost (\texttt{127.0.0.1}) using Python 3, Flask, and the Requests library. A standard web browser serves as the legitimate client. During an experiment, client generators request an intentionally expensive endpoint (\texttt{/work}), saturating the server's worker pool. When a legitimate browser user attempts a health check (\texttt{/health}), the server returns HTTP 503 Service Unavailable. When traffic ceases, the server automatically recovers.

\subsection{Objectives}
The primary objectives of this laboratory assignment are:
\begin{enumerate}[leftmargin=*]
    \item Implement a multithreaded HTTP dummy server with deliberately constrained concurrency capacity.
    \item Model finite resource exhaustion using a bounded semaphore ($C = 4$ worker slots) and simulated processing delay ($T_p = 0.25\,\text{s}$).
    \item Implement a controlled single-source DoS traffic scenario.
    \item Implement a simulated multi-process botnet cluster DDoS scenario.
    \item Observe the visual impact in real-time from a legitimate web browser client.
    \item Record quantitative metrics (request throughput, HTTP 200 vs. 503 counts, latency ranges).
    \item Verify instantaneous system recovery after attack traffic ceases.
\end{enumerate}

\section{DoS and DDoS Concepts}
A Denial of Service (DoS) attack originates from a single logical source or IP address, creating sufficient concurrent traffic to exhaust the target's capacity. A Distributed Denial of Service (DDoS) attack leverages multiple coordinated sources (often termed a botnet), such that their aggregated traffic swamps capacity while circumventing simple single-IP rate-limiting thresholds.

\section{Server Implementation}

\subsection{Socket Setup and Local Binding}
The server is constructed using Python's Flask WSGI framework. To guarantee complete safety, the server explicitly binds only to the IPv4 loopback address \texttt{127.0.0.1} on port \texttt{5000}. This prevents any inbound connections from external devices on the physical local area network.

\subsection{Worker Reservation and Overload Handling}
Concurrency control is implemented using \texttt{threading.BoundedSemaphore(4)}. When a request arrives at \texttt{/work} or \texttt{/health}, the server executes a non-blocking acquisition attempt:

\begin{lstlisting}[language=Python, caption={Thread-safe non-blocking worker slot acquisition}]
slots = threading.BoundedSemaphore(4)
stats = {"accepted": 0, "rejected": 0}
lock = threading.Lock()

@app.get("/work")
def work():
    # Attempt non-blocking slot reservation
    acquired = slots.acquire(blocking=False)
    if not acquired:
        with lock:
            stats["rejected"] += 1
        return jsonify({
            "status": "busy",
            "message": "Server capacity is currently full"
        }), 503

    try:
        time.sleep(0.25)  # Simulated expensive workload
        with lock:
            stats["accepted"] += 1
        return jsonify({"status": "ok", "message": "Request processed"}), 200
    finally:
        slots.release()
\end{lstlisting}

If all 4 slots are busy, the request is immediately rejected with HTTP 503 Service Unavailable without hanging the thread or causing process termination.

\section{Traffic Generator Implementation}

\subsection{Single-Source DoS Simulation (\texttt{client.py})}
The single-source DoS client dispatches a batch of 80 requests in rapid succession with a minimal 0.01s interval. Because each accepted request occupies a worker slot for 0.25s, the arrival rate substantially exceeds the server's processing rate, causing subsequent requests to be rejected.

\subsection{Multi-Bot DDoS Simulation (\texttt{ddos\_sim.py})}
The DDoS simulator utilizes Python's \texttt{multiprocessing.Pool(4)} to spawn four concurrent worker processes representing distributed bots. Each bot sends 25 requests to \texttt{/work}, generating 100 aggregate requests hitting the server simultaneously.

\section{Legitimate Browser Client}
The interactive website provides a real-time health indicator. When the user clicks \textbf{Check Server}, an asynchronous JavaScript \texttt{fetch('/health')} probe is executed:
\begin{itemize}[leftmargin=*]
    \item \textbf{\texttt{SERVER ONLINE}:} Rendered in green with HTTP 200 OK and response latency in milliseconds.
    \item \textbf{\texttt{SERVER OVERLOADED}:} Rendered in red with HTTP 503 Service Unavailable when the worker pool is saturated.
    \item \textbf{\texttt{SERVER UNAVAILABLE}:} Rendered when connection errors or network timeouts occur.
\end{itemize}

The entire experiment is self-contained and reproducible using standard Python tools:
\begin{enumerate}[leftmargin=*]

    \item Launch the target web server: \texttt{python server.py}
    \item Open \texttt{http://127.0.0.1:5000/} in any web browser and click \textbf{Check Server} to verify normal baseline operation.

    \item Start the DoS traffic generator: \texttt{python client.py}
    \item During the attack, click \textbf{Check Server} in the browser and observe the HTTP 503 \texttt{SERVER OVERLOADED} status.
    \item Run the DDoS cluster simulation: \texttt{python ddos\_sim.py}
    \item Once traffic ceases, click \textbf{Check Server} again to verify instantaneous recovery.
\end{enumerate}

\subsection{Interpretation}
\begin{itemize}[leftmargin=*]
    \item \textbf{Baseline Performance:} Under normal conditions, request rate is low ($\lambda \le \mu$). Every request acquires a semaphore slot immediately, resulting in 100\% HTTP 200 responses with an average response time of $264.4\,\text{ms}$ ($250\,\text{ms}$ delay + OS overhead).
    \item \textbf{Resource Exhaustion in DoS/DDoS:} When attack generators flood \texttt{/work}, all 4 slots are occupied continuously. Any incoming request (including the legitimate browser's \texttt{/health} check) cannot acquire a slot and receives an explicit HTTP 503 response. Rejected requests complete in $<12\,\text{ms}$ because no sleep delay is executed.
    \item \textbf{Zero Connection Failures:} The server cleanly returns HTTP 503 instead of dropping TCP connections or crashing, demonstrating graceful degradation under overload.
    \item \textbf{Instant Recovery:} Once the attack scripts terminate, active worker slots drain within $0.25\,\text{s}$, immediately restoring 100\% availability to legitimate browser users.
\end{itemize}

\section{Defensive Countermeasures}
To protect production systems against real-world DoS and DDoS floods:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Token-Bucket Rate Limiting:} Restrict maximum request counts per IP address over time windows.
    \item \textbf{Reverse Proxy Connection Limits:} Use Nginx (\texttt{limit\_conn}, \texttt{limit\_req}) to buffer slow clients and throttle bursts.
    \item \textbf{In-Memory Caching (Redis/Memcached):} Serve repeated static and dynamic responses directly from memory to prevent expensive database or CPU computations.
    \item \textbf{Elastic Load Balancing \& Autoscaling:} Distribute inbound traffic across server pools and dynamically spin up additional instances during traffic surges.
    \item \textbf{Anycast CDN \& WAF Scrubbing (Cloudflare/AWS Shield):} Absorb volumetric DDoS floods at global edge nodes and filter malicious request signatures upstream.
\end{enumerate}

\section{Conclusion}
This laboratory coursework successfully designed, implemented, and evaluated an application-layer DoS and DDoS availability simulation in Python. Bounded semaphore accounting limited the server to 4 concurrent worker slots, delivering explicit HTTP 503 responses when capacity was exceeded. Both single-source and distributed multi-bot attacks caused visible denial of service to a legitimate browser user. The experiment demonstrated the mechanics of availability loss under controlled, safe localhost conditions and verified immediate post-attack recovery.

\section{Viva Voce Examination Preparation Guide}

\begin{enumerate}[leftmargin=*]
    \item \textbf{What is the difference between DoS and DDoS?} \\
    \textit{Ans:} A DoS attack originates from a single source/IP address; a DDoS attack originates from multiple distributed sources (e.g., botnets), making origin-based blocking much more challenging.

    \item \textbf{Why does server capacity matter?} \\
    \textit{Ans:} Server computational resources (worker threads, memory, CPU) are finite. When the arrival rate exceeds capacity ($\lambda > \mu$), queues overflow and excess requests are rejected.

    \item \textbf{Why did we measure a baseline first?} \\
    \textit{Ans:} To establish normal operating performance under healthy conditions (100\% success rate), providing a control benchmark for comparison.

    \item \textbf{What does HTTP 503 mean in this experiment?} \\
    \textit{Ans:} HTTP 503 Service Unavailable indicates that all 4 concurrency slots were occupied, so the server deliberately rejected the excess request to prevent system failure.

    \item \textbf{Why is our localhost DDoS considered an educational simulation?} \\
    \textit{Ans:} Real DDoS attacks originate from distributed internet hosts across distinct public IPs. In this lab, separate local OS processes simulate distributed sources safely on localhost.

    \item \textbf{What resources can a real DoS/DDoS attack exhaust?} \\
    \textit{Ans:} Network bandwidth, socket tables, TCP connection states, CPU time, memory buffers, and database connection pools.

    \item \textbf{How can an enterprise web server defend against request floods?} \\
    \textit{Ans:} By employing rate limiting, reverse-proxy connection throttling, in-memory caching, load balancing, Anycast CDNs, and WAF traffic scrubbing.

    \item \textbf{Why must testing be restricted to systems you own or have permission to test?} \\
    \textit{Ans:} Launching unauthorized attacks against external systems is illegal, unethical, and disruptive. Localhost testing ensures total safety while demonstrating key concepts.
\end{enumerate}

\subsection{Target Web Server (\texttt{code/server.py})}
\begin{lstlisting}[language=Python]
from flask import Flask, jsonify, render_template_string
import threading, time

app = Flask(__name__)
CAPACITY = 4
PROCESSING_TIME = 0.25

slots = threading.BoundedSemaphore(CAPACITY)
stats = {"accepted": 0, "rejected": 0, "health_checks": 0}
lock = threading.Lock()

@app.get("/health")
def health():
    acquired = slots.acquire(blocking=False)
    if not acquired:
        with lock: stats["rejected"] += 1
        return jsonify({"status": "busy", "message": "Server capacity full"}), 503
    try:
        with lock: stats["health_checks"] += 1
        return jsonify({"status": "ok", "message": "Server is healthy"}), 200
    finally:
        slots.release()

@app.get("/work")
def work():
    acquired = slots.acquire(blocking=False)
    if not acquired:
        with lock: stats["rejected"] += 1
        return jsonify({"status": "busy", "message": "Server capacity full"}), 503
    try:
        time.sleep(PROCESSING_TIME)
        with lock: stats["accepted"] += 1
        return jsonify({"status": "ok", "message": "Request processed"}), 200
    finally:
        slots.release()

if __name__ == "__main__":
    app.run(host="127.0.0.1", port=5000, threaded=True)
\end{lstlisting}
