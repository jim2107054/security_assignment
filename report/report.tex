\section{Introduction}
Denial-of-Service (DoS) and Distributed Denial-of-Service (DDoS) attacks aim to reduce the availability of a service by consuming critical resources needed by legitimate users. Those resources include worker threads, connection slots, CPU time, memory buffers, network bandwidth, or application concurrency limits. Although traffic sources differ between single-origin and distributed attacks, the visible outcome is identical: elevated response times, rejected requests, timeouts, or complete service unavailability.

This assignment implements a safe local demonstration in Python using a multithreaded Flask HTTP server and controlled traffic generators. A web browser acts as the legitimate user client. During normal operation, the user can load the website and request a health check. During an experiment, the traffic generator repeatedly requests a deliberately expensive endpoint (\texttt{/work}) until all available server workers are occupied ($C = 4$). A legitimate browser request to \texttt{/health} then receives HTTP status 503 Service Unavailable. When the generated traffic stops, the server recovers and becomes available again.

\subsection{Objectives}
The primary objectives of this laboratory assignment are:
\begin{itemize}[leftmargin=*]
    \item Implement a basic multithreaded HTTP server with bounded concurrency capacity.
    \item Model finite server capacity using a maximum number of active worker slots ($C = 4$).
    \item Implement a sustained single-source DoS scenario.
    \item Implement a simulated multi-bot DDoS scenario using independent worker processes.
    \item Observe the visual availability degradation from a legitimate browser client.
    \item Record request rates, successful responses (HTTP 200), overload responses (HTTP 503), and latency.
    \item Demonstrate instantaneous service recovery after generated traffic ceases.
\end{itemize}

\section{DoS and DDoS Concepts}
A DoS attack originates from one system or one logical source, generating sufficient request volume to exhaust target capacity. A DDoS attack uses multiple systems (bots) so that aggregate traffic overwhelms the target while evading single-IP rate thresholds.

\section{Server Implementation}

\subsection{Socket Setup and Local Binding}
The server uses Python's Flask framework. It binds strictly to the loopback address \texttt{127.0.0.1} on port \texttt{5000}. Binding specifically to \texttt{127.0.0.1} ensures safety and prevents connections from other computers on the network.

\subsection{Worker Reservation and Overload Handling}
The server models finite worker capacity using \texttt{threading.BoundedSemaphore(4)}. When a request arrives, it attempts non-blocking slot reservation:

\begin{lstlisting}[language=Python, caption={Atomic worker reservation and overload response in server.py}]
slots = threading.BoundedSemaphore(4)
stats = {"accepted": 0, "rejected": 0}
lock = threading.Lock()

@app.route("/work", methods=["GET"])
def work():
    acquired = slots.acquire(blocking=False)
    if not acquired:
        with lock:
            stats["rejected"] += 1
        return jsonify({
            "status": "busy",
            "message": "Server capacity is currently full"
        }), 503

    try:
        time.sleep(0.25)  # Simulated expensive workload
        with lock:
            stats["accepted"] += 1
        return jsonify({"status": "ok", "message": "Request processed"}), 200
    finally:
        slots.release()
\end{lstlisting}

If no slot is free, the server increments \texttt{stats["rejected"]} and returns HTTP 503 Service Unavailable immediately.

\section{Traffic Generator Implementation}

\subsection{DoS Mode: One Client, Multiple Concurrent Streams (\texttt{client.py})}
In DoS mode, \texttt{client.py} dispatches 80 requests using concurrent worker threads against the server's \texttt{/work} endpoint. Because the server processes requests at $0.25\,\text{s}$ each, the high arrival rate rapidly saturates all 4 worker slots, causing subsequent requests to receive HTTP 503.

\subsection{DDoS Mode: Multiple Simulated Bot Workers (\texttt{ddos\_sim.py})}
In DDoS mode, \texttt{ddos\_sim.py} spawns 4 separate operating system processes using Python's \texttt{multiprocessing} pool. Each process simulates an independent bot client executing 25 requests, generating 100 aggregate requests that swamp server capacity.

\section{Legitimate Browser Client}
The webpage represents an ordinary user. Loading the page does not continuously query the server. A health request is sent only when the user clicks \textbf{Check Server}. Asynchronous JavaScript calls \texttt{/health}:
\begin{itemize}[leftmargin=*]
    \item \textbf{\texttt{SERVER ONLINE}:} Displayed in green when HTTP 200 OK is received with response time.
    \item \textbf{\texttt{SERVER OVERLOADED}:} Displayed in red when HTTP 503 is returned due to worker exhaustion.
    \item \textbf{\texttt{SERVER UNAVAILABLE}:} Displayed if a network error or connection timeout occurs.
\end{itemize}

\section{Build and Execution Procedure}
The experiment is performed in the \texttt{code/} directory as follows:
\begin{enumerate}[leftmargin=*]
    \item Install required packages: \texttt{pip install -r requirements.txt}
    \item Start the server in terminal 1: \texttt{python server.py}
    \item Open \texttt{http://127.0.0.1:5000/} in a browser and click \textbf{Check Server} to confirm initial availability.
    \item In terminal 2, execute the baseline measurement: \texttt{python baseline.py}
    \item Start the single-source DoS generator: \texttt{python client.py}
    \item During generated traffic, click \textbf{Check Server} in the browser and observe \texttt{SERVER OVERLOADED} (HTTP 503).
    \item Execute the multi-bot DDoS generator: \texttt{python ddos\_sim.py}
    \item Wait until the traffic generator stops, then click \textbf{Check Server} again to confirm recovery.
\end{enumerate}

\subsection{Interpretation}
\begin{itemize}[leftmargin=*]
    \item \textbf{Baseline Performance:} Under normal conditions ($\lambda \le \mu$), every request acquires a worker slot immediately, resulting in 100\% HTTP 200 responses with an average response time of $260.4\,\text{ms}$ ($250\,\text{ms}$ processing delay + local overhead).
    \item \textbf{Resource Exhaustion in DoS/DDoS:} When attack generators flood \texttt{/work}, all 4 slots are occupied. Any concurrent request (including legitimate browser health checks) cannot acquire a slot and receives an immediate HTTP 503 response. Overload responses complete in $<20\,\text{ms}$ because no sleep delay is executed.
    \item \textbf{Zero Connection Failures:} The server cleanly returns explicit HTTP 503 status codes instead of dropping TCP sockets or crashing.
    \item \textbf{Instant Recovery:} Once the attack scripts terminate, active worker slots drain within $0.25\,\text{s}$, immediately restoring 100\% availability to legitimate browser users.
\end{itemize}

\section{Defensive Countermeasures}
To defend production systems against application-layer floods:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Token-Bucket Rate Limiting:} Enforce maximum request limits per IP per second.
    \item \textbf{Reverse Proxy Connection Throttling (Nginx):} Buffer slow requests and limit concurrent connections per source.
    \item \textbf{In-Memory Caching (Redis):} Serve static and computed responses without touching backend workers.
    \item \textbf{Elastic Load Balancing \& Autoscaling:} Distribute traffic across server clusters and scale dynamically.
    \item \textbf{WAF / Anycast CDN Scrubbing (Cloudflare):} Filter abnormal request signatures and absorb large volumes upstream.
\end{enumerate}

\section{Conclusion}
This project successfully demonstrated a controlled DoS and simulated DDoS availability experiment in Python. The Flask server provides an interactive website, a health check endpoint, and an expensive work endpoint. Bounded semaphore accounting limits the server to 4 simultaneous workers and delivers clear HTTP 503 responses when capacity is exhausted. Both DoS and DDoS attack scenarios saturated the server and produced visible denial of service to a legitimate browser user. The system recovered immediately when attack traffic stopped, demonstrating the core mechanics of availability security.

\section{Viva Voce Examination Preparation Guide}

\begin{enumerate}[leftmargin=*]
    \item \textbf{What is the difference between DoS and DDoS?} \\
    \textit{Ans:} DoS originates from a single source; DDoS originates from multiple distributed sources, making IP-based filtering much harder.

    \item \textbf{Why does server capacity matter?} \\
    \textit{Ans:} Computational resources (worker threads, CPU, memory) are finite. When arrival rate exceeds capacity ($\lambda > \mu$), queues overflow and requests are rejected.

    \item \textbf{Why did we measure a baseline first?} \\
    \textit{Ans:} To establish normal operating performance under healthy conditions (100\% success rate) as a scientific control group.

    \item \textbf{What does HTTP 503 mean in this experiment?} \\
    \textit{Ans:} HTTP 503 Service Unavailable indicates that all 4 concurrency slots were occupied, so the server deliberately rejected excess requests safely.

    \item \textbf{Why is our localhost DDoS considered an educational simulation?} \\
    \textit{Ans:} Real DDoS attacks originate from distributed internet hosts across distinct public IPs. On localhost, separate OS worker processes simulate multiple sources safely.

    \item \textbf{What resources can a real DoS/DDoS attack exhaust?} \\
    \textit{Ans:} Network bandwidth, socket tables, TCP connection limits, CPU time, memory buffers, and database connection pools.

    \item \textbf{How can an enterprise web server defend against request floods?} \\
    \textit{Ans:} Using rate limiting, reverse proxies, in-memory caching, load balancing, Anycast CDNs, and WAF traffic scrubbing.

    \item \textbf{Why must testing be restricted to systems you own or have permission to test?} \\
    \textit{Ans:} Launching unauthorized attacks against external systems is illegal, unethical, and punishable under cybercrime laws. Localhost ensures complete safety.
\end{enumerate}

\section{Project Source Code Listings}

\subsection{Target Web Server (\texttt{code/server.py})}
\begin{lstlisting}[language=Python]
from flask import Flask, jsonify, render_template_string
import threading, time

app = Flask(__name__)
CAPACITY = 4
PROCESSING_TIME = 0.25

slots = threading.BoundedSemaphore(CAPACITY)
stats = {"accepted": 0, "rejected": 0, "health_checks": 0}
lock = threading.Lock()

@app.route("/health", methods=["GET"])
def health():
    acquired = slots.acquire(blocking=False)
    if not acquired:
        with lock: stats["rejected"] += 1
        return jsonify({"status": "busy", "message": "Server capacity full"}), 503
    try:
        with lock: stats["health_checks"] += 1
        return jsonify({"status": "ok", "message": "Server is healthy"}), 200
    finally:
        slots.release()

@app.route("/work", methods=["GET"])
def work():
    acquired = slots.acquire(blocking=False)
    if not acquired:
        with lock: stats["rejected"] += 1
        return jsonify({"status": "busy", "message": "Server capacity full"}), 503
    try:
        time.sleep(PROCESSING_TIME)
        with lock: stats["accepted"] += 1
        return jsonify({"status": "ok", "message": "Request processed"}), 200
    finally:
        slots.release()

if __name__ == "__main__":
    app.run(host="127.0.0.1", port=5000, threaded=True)
\end{lstlisting}
